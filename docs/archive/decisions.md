## 1. 과제 범위

Phase 1은 파일 기반 SQL 처리기(INSERT/SELECT, CLI), Phase 2는 메모리 기반 B+tree 인덱스와 100만 건 성능 비교, Phase 3은 Thread Pool 기반 API 서버다. 페이지, 버퍼 풀, ARIES는 범위 밖이다. 트랜잭션은 INSERT 배치의 원자성까지만 다룬다. 실질적인 난이도는 Phase 3의 멀티스레드 동시성에 있다.

## 2. 확정된 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 언어 / 환경 | C++17, 리눅스(WSL 또는 Docker) | 팀 결정. 소켓 API, fsync, rename 동작을 하나로 통일 |
| 저장 포맷 | append-only 바이너리. 레코드를 **프레임** 단위로 묶고 프레임마다 CRC32 (직접 구현) | 텍스트 파싱이 없어 선형 탐색이 순수 I/O로 측정됨. 프레임이 원자성의 단위라서 정전 시에도 배치 전체가 남거나 전부 사라짐. `dump` 명령 제공 |
| 인덱스 영속화 | 시작할 때 파일 재스캔으로 인덱스 재구성 | 진실이 파일 하나뿐이라 둘이 어긋날 일이 없음 |
| 인덱스 값 | `id → 레코드 오프셋` | 레코드 전체를 메모리에 올리지 않기 위해 |
| 실행 모델 | 결과를 행 단위로 받는 쪽(sink)에 바로 넘김 (Volcano 방식) | 결과 크기와 무관하게 메모리 일정. CLI와 서버는 받는 쪽만 다름 |
| 동시성 | `std::shared_mutex` (읽기는 shared, 쓰기는 unique) | 단일 writer만으로는 읽기-쓰기 충돌을 막지 못함 |
| 쓰기 순서 | 파일에 먼저 쓰고, 인덱스에는 나중에 공개 | 읽는 쪽이 아직 데이터가 없는 오프셋을 보지 않게 하기 위해 |
| 파일 I/O | `pread`/`pwrite` (fd 기반) | `fstream`은 읽기 위치를 공유해서 멀티스레드에서 안전하지 않음 |
| HTTP | cpp-httplib + 직접 만든 스레드 풀 (`new_task_queue`로 교체) | HTTP 파싱 버그 대신 스레드 풀과 동시성에 집중 |
| API | `POST /query`, 요청 바디는 SQL 평문 | 과제의 "SQL 요청 병렬 처리"와 직접 맞음 |
| 응답 포맷 | INSERT·EXPLAIN은 JSON, SELECT는 NDJSON 스트리밍 (직렬화만 직접 구현) | 입력 JSON 파싱은 필요 없음. 스트리밍 중 실패는 마지막 줄로 알림 |
| 빌드 / 테스트 | CMake + GoogleTest | 빌드 설정은 AI에게 위임. 검증 기준은 사람이 정함 |
| 역할 분담 | 사람은 Phase별 결정과 지시서, Claude Code는 전체 구조와 세부 명세와 구현 | 결정은 사람이, 구조 설계와 구현은 AI가. 명세는 코드보다 먼저 승인 |

## 3. Phase 1 세부 결정

| # | 항목 | 결정 |
|---|---|---|
| 1 | id 부여 | 엔진이 자동 부여, 사용자가 id를 넣으면 `SchemaError` |
| 2 | 타입 | `INT`(int64), `VARCHAR(n)`. NULL 없음 |
| 3 | WHERE | `컬럼 = 값` 하나만 |
| 4 | Statement 표현 | `std::variant<InsertStmt, SelectStmt>` + `std::visit` |
| 5 | 에러 | 타입별 예외: `ParseError`, `SchemaError`, `StorageError` → Phase 3에서 400 / 404·400 / 500 |
| 6 | 파일 손상 | 아래 "손상 판정 규칙" 참고 (프레임 단위) |
| 7 | 내구성 | 프레임마다 `write`, `fsync`는 1초 주기 + 종료 시 |
| 8 | 결과 전달 | 행 단위로 sink에 전달. CLI는 스키마 폭으로 정렬해 바로 출력 |
**프레임 포맷**
- `frame = frame_len u32 | record_count u32 | 레코드들 | crc32 u32`
- `record = payload_len u32 | payload(id i64 + 필드들)`
- INSERT 한 문장은 레코드 1개짜리 프레임, Phase 3 배치는 레코드 N개짜리 프레임
- 상한: `payload_len` 64KB, `frame_len` 4MB

**id 부여 구현**
- `Table`이 `int64_t nextId_`를 가진다. unique_lock 안에서만 읽고 쓰므로 atomic이 필요 없다.
- 시작할 때 재스캔에서 본 가장 큰 id + 1로 정한다. 빈 테이블이면 1. 레코드 수 + 1이 아니라 최댓값 + 1을 쓴다.
- 프레임 쓰기가 성공한 뒤에만 `nextId_`를 올린다. 실패한 INSERT는 id를 소모하지 않는다.
- `INT64_MAX`에 도달하면 `StorageError`. id는 재사용하지 않는다.

**손상 판정 규칙 (프레임 단위)**
- magic 또는 version 불일치: `StorageError`, 시작 거부
- 불완전하거나 CRC가 틀린 프레임이 파일 끝에 닿음(꼬리 손상): 프레임 시작 위치로 `ftruncate`, 경고 로그 후 정상 시작
- 잘못된 프레임 뒤에 바이트가 더 남아 있음(중간 손상): `StorageError`, 시작 거부
- 정상 프레임이라도 내부 레코드가 `frame_len`과 `record_count`에 맞지 않으면 중간 손상
**내구성 규칙**
- 보장 수준: 프로세스 크래시에는 데이터 손실 없음. 정전 시 마지막 약 1초 분량 손실 가능. 어느 경우든 프레임은 전부 남거나 전부 사라짐
- 주기 fsync는 백그라운드 스레드가 1초마다 수행
- 정상 종료 순서: 새 연결 거절 → 큐의 작업과 처리 중인 작업 완료 → `fsync` → 파일 닫기
- SIGINT/SIGTERM: 시그널 핸들러는 `std::atomic<bool>` 플래그만 세우고, 실제 종료는 메인 루프가 수행
- `fsync` 실패: 재시도하지 않고 에러 로그 후 서버 중지(fail-stop)
- 테이블 파일을 새로 만들었으면 파일과 디렉터리를 모두 `fsync`
- CLI 모드: SQL 파일 실행이 끝나면 `fsync` 후 종료

## 4. Phase 2 세부 결정

| # | 항목 | 결정 | 이유 |
|---|---|---|---|
| 1 | 노드 크기 | 컴파일 시간 템플릿 인자. 실제 128, 테스트 3·4 | 높이 3~4로 낮게. 테스트는 작게 해서 연쇄 분할을 매번 검증 |
| 2 | 분할 정책 | 평소 반반 분할, 재시작 때 bulk loading | 삽입 경로는 표준 방식으로 단순하게. 순차 삽입으로 반쯤 빈 리프는 재시작 때 꽉 채움 |
| 3 | 노드 메모리 모양 | 노드 안 고정 크기 배열, 키와 값 배열 분리 (SoA) | 키가 노드 안에 연속으로 있어 이진 탐색이 캐시 친화적. `vector`는 추가 점프 발생 |
| 4 | 노드 타입 | 리프와 내부 노드를 별도 구조체로, 공통 `isLeaf` 헤더, 가상 함수 없음 | 리프마다 쓰지 않는 자식 배열을 두지 않음 |
| 5 | 분할 시점 | bottom-up + 경로 스택, 부모 포인터 없음 | 트리 전체를 락 하나로 보호하므로 top-down의 동시성 장점이 필요 없음 |
| 6 | 메모리 소유 | 자식은 `unique_ptr`, 리프 `next`는 일반 포인터 | 이중 소유와 이중 해제 방지 |
| 7 | 분할 규칙 | 리프는 copy-up, 내부 노드는 push-up | 리프의 키는 데이터라 남아야 하고, 내부 키는 안내용이라 옮겨 감 |
| 8 | EXPLAIN | 넣음. `IndexScan(t, id=v)` / `FullScan(t[, filter c=v])` | 인덱스 사용 여부를 기능 테스트와 시연에서 바로 확인 |
| 9 | 벤치마크 설계 | 테스트 단계에서 결정 (Claude Code가 명세에서 제안) | |

## 5. Phase 3 세부 결정

| # | 항목 | 결정 | 이유 |
|---|---|---|---|
| 1 | 워커 수 | 기본 CPU 코어 수, `--workers`로 변경 | CPU 위주 작업이라 코어 수 이상은 이득 없음. 숫자는 측정 후 조정 |
| 2 | 큐 크기 | 기본 1024, `--queue`로 변경. 꽉 차면 503 | 큐가 길수록 대기 시간이 늘어남(리틀의 법칙) |
| 3 | 서버 설정 | 실행 옵션만 사용. 바디 1MB 상한(413), 타임아웃 5초, keep-alive, `GET /health` | 느린 클라이언트와 큰 요청으로부터 워커 보호 |
| 4 | 요청 형태 | SELECT 하나, EXPLAIN 하나, 또는 INSERT 1~1000개. 그 외는 400 | 결과 해석이 애매한 혼합 요청 금지, 워커 독점 방지 |
| 5 | 원자 배치 | INSERT만, 한 테이블만. 전체 검증 후 프레임 하나로 커밋, 실패 시 전부 취소 | 여러 쓰기를 한 번에. SELECT 혼합은 read-your-writes가 필요해서 리팩터링으로 미룸 |
| 6 | 큰 결과 | NDJSON 스트리밍, 행 수 상한 없음. 성공 여부는 마지막 줄 | 실제 DB처럼 만들면서 보내기. 상태 코드는 첫 바이트 전에 생긴 에러에만 의미 |
| 7 | 읽기 일관성 | 스캔 시작 시 `fileSize`를 끝 지점으로 고정 | 스트리밍 중 커밋된 배치가 섞이지 않음. 끝 지점은 항상 프레임 경계 |
| 8 | 처리량 비교 실험 | 테스트 단계에서 결정 | |

## 6. 리팩터링 후보

- **NULL과 추가 타입**: 인코딩에 null 비트맵 추가, 비교와 출력은 3값 논리
- **WHERE 확장**: `AND`/`OR`, `<` `>` `BETWEEN`. 범위 조건은 B+tree 리프 순회로 처리
- **LIMIT과 키셋 페이지네이션**: `WHERE id > x LIMIT n`을 B+tree 범위 탐색으로
- **SELECT를 포함한 배치 (read-your-writes)**: 배치 안 SELECT가 아직 커밋 전인 같은 배치의 행을 보도록
- **여러 테이블 배치**: 테이블별 락 순서 고정 필요
- **DELETE**: 추가하면 "최댓값 + 1" 방식에서 id 재사용 문제가 생김 → `nextId` 영속화 필요
- **맨 오른쪽 특수 분할**: 순차 삽입 시 리프 충전율 개선, 반반 분할과 충전율 비교
- **보조 인덱스**: id 외 컬럼 인덱스, 중복 키 처리 필요
- **group commit**: 여러 요청의 프레임을 모아 fsync 한 번으로 처리
- **prepared statement**: 한 번 파싱한 쿼리를 값만 바꿔 재실행
- **REST → AST 매핑**: SQL 문자열로 번역하지 않고 AST로 바로 번역 (SQL Injection 방지, 파싱 한 번)
- **HTTP와 JSON 직접 파싱**
- **인덱스 스냅샷**: 체크포인트 오프셋 기록, 원자적 교체, 나머지 보충, 재스캔 대비책

## 7. 검증 기준 (초안)

검증 기준은 사람이 정하고, 테스트 코드는 AI가 작성한다. 상세 완료 조건은 각 Phase 지시서에 있다.

**Phase 1**
- Lexer: 문자열 안의 `,` `;`, `''` 이스케이프, 키워드 대소문자, 닫히지 않은 따옴표
- Parser: 문법 오류, 값 개수와 컬럼 수 불일치, 타입 불일치, id 직접 입력 거절
- Storage: 왕복 일치, 꼬리 손상 프레임 잘라내기, 중간 손상 시작 거부, magic 불일치 거부, record_count 불일치 거부
- 원자 쓰기: 쓰기 실패를 주입해도 파일 크기와 `nextId` 그대로
- id: 재시작 후 이어지는 id, 실패한 INSERT 뒤 id 연속성
- 결과가 스캔이 끝나기 전부터 출력됨

**Phase 2**
- 트리 불변식 `validate()`: 키 정렬, 모든 리프의 깊이 동일, 노드 키 수 범위, 내부 경계값 = 오른쪽 서브트리 최솟값, 리프 연결 순서
- 노드 크기 3·4·128에서 무작위 삽입·검색, 루트 분할까지 연쇄 분할 포함
- bulk loading으로 만든 트리와 삽입으로 만든 트리의 검색 결과 일치
- 100만 건 INSERT 후 무작위 id 조회 결과가 선형 탐색 결과와 일치
- 레코드 여러 개짜리 프레임의 모든 id가 커밋 후와 재시작 후 검색됨
- 재시작 후 건수와 `nextId` 복원, 없는 id, 빈 테이블, EXPLAIN 출력

**Phase 3**
- 스레드 N개 × 각 M건 동시 INSERT: 총 건수 N × M, id 중복 없음, `validate()` 통과, ThreadSanitizer 통과
- 배치 원자성: 잘못된 문장 하나면 전체 거절, 쓰기 실패 주입 시 전부 취소, 프레임 중간에서 잘린 파일은 재시작 후 배치 전체가 사라짐, K건 배치가 동시에 커밋되는 동안 모든 스캔의 행 수가 K의 배수
- 스트리밍: 100만 행 SELECT가 일정한 메모리로 끝남, 중간 실패 시 마지막 줄 `"ok":false`
- 요청 형태: 빈 바디·혼합·SELECT 여러 개·1000개 초과는 400, 1MB 초과는 413, 큐 가득 503, 없는 테이블 404
- SIGTERM 수신 후 처리 중이던 요청이 끝나고, 커밋된 행이 재시작 후 남아 있음
