# 결정 요약: 사람이 정한 것

팀원과 공유하는 한 장짜리 요약이다. 사람이 정한 규칙(`architecture.md`의 `[고정]`)과 사람이 AI 추천을 받아들인 결정(위임)만 모았다. Phase 순서가 아니라 **주제별**로 묶었다.

- 원본은 `architecture.md`다. 이 문서는 거기서 뽑은 사본이다. 둘이 다르면 `architecture.md`가 맞다.
- `[고정]` 규칙이나 사람·위임 결정이 바뀌면 같은 커밋에서 이 문서도 고친다.
- AI가 정한 세부(빌드 플래그, 출력 폭, 서버 튜닝 등)는 여기 없다. `decisions.md`에서 "정한 사람 = AI"인 줄을 보면 된다.
- 표의 "정한 사람"은 다음과 같다. **사람**: 직접 고름. **위임**: AI 추천을 "추천대로"로 받음. 위임 결정은 이유를 직접 설명할 수 있어야 한다(`explain-log.md`).

## 3. 파일 저장 포맷

테이블 하나 = 파일 두 개: `data/<표>.schema`(컬럼 정의, 텍스트)와 `data/<표>.tbl`(데이터, 바이너리).

| 결정 | 이유 | 정한 사람 | 원본 |
|---|---|---|---|
| `.schema`는 한 줄에 컬럼 하나(`name VARCHAR(32)`). 숨은 첫 컬럼 `id`는 적지 않음 | 단순한 텍스트 | 사람 | §5.1 |
| `.tbl`은 **append-only 바이너리**. 뒤에 붙이기만 함 | 텍스트 파싱이 없어 선형 탐색이 순수 I/O로 측정됨 | 사람 | §5.2 |
| 레코드를 **프레임** 단위로 묶고 프레임마다 CRC32 | 프레임 = 원자성 단위. 정전이 나도 배치 전체가 남거나 전부 사라짐 | 사람 | §5.2 |
| 정수는 little-endian, 한 바이트씩 직접 씀. 구조체 `memcpy` 금지 | 컴파일러가 구조체에 넣는 빈칸 때문에 디스크 형식이 흔들리지 않게 | 사람 | §4 |
| 테이블 파일 I/O는 `pread`/`pwrite`. `fstream` 금지 | `fstream`은 읽기 위치를 공유해서 멀티스레드에서 안전하지 않음 | 사람 | §4 |
| 상한: 레코드 64 KiB, 프레임 4 MiB | 손상된 길이 필드가 엄청난 크기를 주장하지 못하게 | 사람 | §5.2 |

```
.tbl   = [헤더 8B: "MDB1" + 버전 1 + 예약 0] [프레임] [프레임] ...
프레임 = frame_len | record_count | 레코드들 | crc32
레코드 = payload_len | id | 스키마 순서의 필드들 (INT 8B, VARCHAR = 길이 2B + 바이트)
```

## 4. 쓰기 규칙

| 결정 | 이유 | 정한 사람 | 원본 |
|---|---|---|---|
| 쓰는 순서: **파일 바이트 → 파일 크기(fileSize) → 다음 id → 인덱스** | 읽는 쪽이 아직 없는 바이트를 가리키는 오프셋을 보지 않게 | 사람 | §5.4, §12 |
| 쓰기 실패 → 쓰다 만 부분을 `ftruncate`로 자르고 에러. 파일 크기·id는 그대로 | 실패한 INSERT는 흔적을 남기지 않음 | 사람 | §5.4 |
| 자르기까지 실패 → 그 테이블만 **쓰기 불가**로 표시. 읽기는 정상 | 손상 범위를 테이블 하나로 가둠. 남은 바이트는 재시작 때 꼬리 손상으로 정리됨 | 위임 (#4) | §5.4 |
| 열린 뒤에는 읽을 때마다 CRC를 다시 계산하지 않음 | 시작할 때 이미 검증한 바이트라서 | 사람 | §5.3 |

## 5. 복구와 손상 판정

서버나 CLI가 시작할 때 `.tbl`을 처음부터 끝까지 읽으며 검사한다. 손상은 위치에 따라 두 종류로 나눈다.

| 상황 | 처리 | 정한 사람 | 원본 |
|---|---|---|---|
| 헤더 magic·버전 불일치 | 시작 거부 | 사람 | §5.3 |
| **꼬리 손상**: 마지막 프레임이 덜 써졌거나 CRC가 틀리고, 그게 파일 끝 | 잘라낸 뒤 경고하고 정상 시작 | 사람 | §5.3 |
| 꼬리를 자르기 전에 잘릴 바이트를 `.torn` 파일로 복사 | 잘못 판정했어도 데이터 손실 0 | 위임 (#2) | §5.3 |
| `frame_len`이 범위(16 B~4 MiB) 밖이면 위치와 상관없이 **중간 손상** | 길이 필드가 깨지면 정상 프레임까지 꼬리로 오인해 자르던 문제를 막음 | 위임 (#2) | §5.3 |
| **중간 손상**: 깨진 프레임 뒤에 데이터가 더 있음. 또는 레코드 수·길이가 프레임과 안 맞음 | 시작 거부 (사람이 봐야 함) | 사람 | §5.3 |
| 파일이 8 B(헤더)보다 짧음 | 헤더를 다시 쓰고 시작 | 위임 (#5) | §5.3 |

핵심 구분: **꼬리**는 "쓰다가 죽음"이라 자르면 정상이다. **중간**은 "디스크나 사람이 망가뜨림"이라 자동으로 고치면 안 된다.

## 6. id 규칙

| 결정 | 이유 | 정한 사람 | 원본 |
|---|---|---|---|
| id는 엔진이 자동으로 붙임. 사용자가 id를 넣으면 에러 | 유일성을 엔진이 보장 | 사람 | §7.1 |
| 다음 id = 파일에서 본 **최대 id + 1** (빈 테이블은 1). 레코드 수 + 1이 아님 | 실패·손상으로 번호가 비어도 겹치지 않음 | 사람 | §5.3 |
| 실패한 INSERT는 id를 쓰지 않음. id는 재사용하지 않음 | 4장의 쓰기 순서에서 자연히 나옴 | 사람 | §5.4 |
| `INT64_MAX`에 닿으면 에러 | 오버플로 방지 | 사람 | §5.4 |

## 7. 내구성 (fsync)

`write`가 끝나도 데이터는 OS 캐시에 있다. `fsync`를 해야 디스크에 내려간다.

| 결정 | 이유 | 정한 사람 | 원본 |
|---|---|---|---|
| 보장 수준: 프로세스 크래시에는 손실 0, 정전 시 마지막 약 1초 손실 가능. 어느 경우든 프레임은 전부 남거나 전부 사라짐 | 매 쓰기마다 fsync하면 너무 느림 | 사람 | §5.6 |
| 서버: 백그라운드 스레드가 1초마다 fsync. 실패하면 재시도 없이 서버 중지(fail-stop) | fsync 실패 후 재시도는 데이터가 내려갔는지 보장하지 못함 | 사람 | §5.6, §11.5 |
| CLI: SQL 파일 실행이 끝나면 fsync하고 종료 | | 사람 | §5.6 |
| 새 파일은 파일과 디렉터리 모두 fsync | 디렉터리를 fsync하지 않으면 파일 자체가 사라질 수 있음 | 사람 | §5.6 |

## 9. 실행 엔진

| 결정 | 이유 | 정한 사람 | 원본 |
|---|---|---|---|
| 결과를 모으지 않고 **한 줄씩** 받는 쪽(RowSink)에 넘김 (Volcano 방식) | 결과 크기와 무관하게 메모리 일정. CLI와 서버는 받는 쪽만 다름 | 사람 | §2, §7.3 |
| 받는 쪽이 "그만"(false)을 돌려주면 실행기가 멈춤 | 끊긴 클라이언트 때문에 워커가 스캔을 끝까지 하지 않게 | 위임 (#3) | §7.3 |
| 문장 표현은 `std::variant` + `std::visit` | 새 문장 종류를 추가하면 처리 누락이 컴파일 에러로 드러남 | 사람 | §2 |
| 에러는 타입별 예외 3개: `ParseError`, `SchemaError`, `StorageError` | P3에서 HTTP 상태 코드로 바로 연결 | 사람 | §2 |
| 실행기에 접근 경로(전체 스캔/인덱스)를 고르는 지점을 P1부터 둠 | P2에서 인덱스를 끼울 때 위 계층을 고치지 않게 | 사람 | §2 |
| `WHERE id = 정수`일 때만 인덱스, 나머지는 전체 스캔 | 인덱스는 id에만 있음 | 사람 | §7.2 |
| 인덱스 조회도 같은 RowSink로 0~1행을 넘김 | CLI·서버가 접근 경로를 몰라도 됨 | 사람 | §7.3 |
| 파일 쓰기에 테스트용 장애 주입 이음새(`FileIO`)를 둠 | 쓰기 실패·자르기 실패를 테스트에서 재현 | 사람 | §2, §14.1 |
| EXPLAIN 출력: `IndexScan(t, id=v)` / `FullScan(t)` / `FullScan(t, filter c=v)` | 인덱스 사용 여부를 시연에서 바로 확인 | 사람 | §7.2 |

## 10. 인덱스 (B+ 트리)

| 결정 | 이유 | 정한 사람 | 원본 |
|---|---|---|---|
| 메모리 B+ 트리, `id → 파일 위치(오프셋)` | 레코드 전체를 메모리에 올리지 않음 | 사람 | §9.1 |
| 인덱스는 디스크에 저장하지 않음. **시작할 때 파일을 다시 읽어 재구성** | 진실이 파일 하나뿐이라 둘이 어긋날 일이 없음 | 사람 | §9.1 |
| 노드 크기는 컴파일 시간 인자. 운영 128, 테스트 3·4 | 운영은 높이를 낮게, 테스트는 분할이 자주 일어나게 | 사람 | §9.1 |
| 노드 안은 고정 배열, 키·값 배열 분리. 노드 안 `vector` 금지 | 이진 탐색이 캐시 친화적 | 사람 | §9.1 |
| 리프·내부 노드는 별도 구조체, 가상 함수 없음 | 리프에 쓰지 않는 자식 배열을 두지 않음 | 사람 | §9.1 |
| 분할은 아래에서 위로(경로 스택), 부모 포인터 없음 | 트리 전체를 락 하나로 보호하므로 위→아래 방식의 장점이 없음 | 사람 | §9.1 |
| 리프 분할은 copy-up, 내부 노드 분할은 push-up | 리프 키는 데이터라 남아야 하고, 내부 키는 안내용이라 옮겨 감 | 사람 | §9.1 |
| 평소 반반 분할, 재시작 때 벌크 로딩으로 꽉 채움 | 삽입은 단순하게, 공간 효율은 재시작 때 회복 | 사람 | §9.1 |
| `validate()`가 불변식 5개 검사 (키 정렬, 리프 깊이 동일, 키 개수 범위, 경계값 = 오른쪽 최솟값, 리프 연결 순서) | 테스트에서 트리가 깨졌는지 기계적으로 확인 | 사람 | §9.4 |

## 11. 동시성

| 결정 | 이유 | 정한 사람 | 원본 |
|---|---|---|---|
| 락은 P3에서 테이블마다 `std::shared_mutex` 하나 (읽기 shared, 쓰기 unique) | 쓰는 쪽을 하나로 줄이는 것만으로는 읽기-쓰기 충돌을 막지 못함 | 사람 | §12 |
| **`Table`만** 파일·인덱스·id·락을 만짐. 그 위 계층은 락을 모름 | 동시성 버그가 생길 곳을 한 클래스로 가둠 | 사람 | §2 |
| 스캔 시작 시점의 파일 크기를 끝 지점으로 고정(스냅샷) | 스트리밍 중에 커밋된 배치가 섞이지 않음. 끝 지점은 항상 프레임 경계 | 사람 | §5.5 |
| 파일 읽기는 락을 놓은 뒤에 함 | 4장의 쓰기 순서 덕분에 안전. 읽기가 쓰기를 오래 막지 않음 | 사람 | §12 |

## 12. API 서버

| 결정 | 이유 | 정한 사람 | 원본 |
|---|---|---|---|
| cpp-httplib + 직접 만든 스레드 풀(`new_task_queue`로 교체) | HTTP 파싱 대신 스레드 풀·동시성에 집중 | 사람 | §11.1 |

| `POST /query`, 바디는 SQL 평문 | 과제의 "SQL 요청 병렬 처리"와 직접 맞음 | 사람 | §11.1 |
| 한 요청 = SELECT 1개, EXPLAIN 1개, 또는 INSERT 1~1000개. 그 외는 400 | 결과 해석이 애매한 혼합 요청 금지, 워커 독점 방지 | 사람 | §11.2 |
| INSERT 배치는 한 테이블만. 전부 검증 → 프레임 하나로 커밋 → 실패하면 전부 취소 | 여러 쓰기를 한 번에, 일부만 반영되는 일 없음 | 사람 | §11.3 |
| 응답: INSERT·EXPLAIN은 JSON, SELECT는 NDJSON 스트리밍. 성공 여부는 **마지막 줄** | 결과 크기 상한 없이 보내면서 보냄. 상태 코드는 첫 바이트 전 에러에만 의미 | 사람 | §11.4 |
| 상태 코드: 문법 400, 없는 테이블 404, 그 외 스키마 400, 저장소 500, 큐 가득 503, 바디 초과 413 | 예외 타입과 1:1 | 사람 | §11.4 |
| 종료: 시그널 핸들러는 플래그만 세움 → 새 연결 거절 → 처리 중 작업 완료 → fsync → 닫기 | 시그널 핸들러 안에서는 안전한 일이 거의 없음 | 사람 | §11.5 |
