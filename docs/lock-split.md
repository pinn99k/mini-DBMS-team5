# 락 분리: 쓰기 I/O를 공유 락 밖으로

## 1. 한 줄 요약

쓰는 쪽이 독점 락을 쥔 채 `pwrite`까지 해서, 읽는 쪽이 그동안 잠들었다. `pwrite`를 락 밖으로 빼자 **혼합 부하(읽기 90%) 2스레드 처리량이 473k → 770k ops/s(+63%)**, 락 때문에 잠드는 횟수가 **작업 1,000개당 86 → 20회(-77%)** 가 됐다.

## 2. 처음 결론과, 그게 틀린 이유

MVP 때 `bench.md` §5는 "shared_mutex가 읽기도 독점 락인 경우보다 빠르지 않다"고 결론 냈다.

이 결론은 **1.5초짜리 측정을 한 번** 돌린 결과였다. 이 환경(vCPU 2개)은 같은 설정을 다시 돌려도 처리량이 ±25% 흔들린다. 다섯 번 반복해 중앙값을 보면 반대다.

| 읽기 전용, 2스레드 | 중앙값 | 범위 (5회) | 잠든 횟수 / 1,000 작업 |
|---|---:|---:|---:|
| shared_mutex | 1,392k | 1,191k ~ 1,567k | 0 |
| 읽기도 독점 락 | 769k | 580k ~ 1,270k | 25 |

shared가 약 1.8배 빠르다. 독점 락에서는 락을 잡는 구간이 트리 조회(수백 ns)뿐인데도 두 스레드가 부딪치면 한쪽이 잠들고, **잠들었다 깨는 비용(수 µs)이 락 구간보다 훨씬 크다.** 그래서 구간이 짧아도 공유 락이 이득이다.

교훈: 확률적으로 흔들리는 측정은 반복해서 범위까지 본다. 이번에는 "잠든 횟수"(`getrusage`의 자발적 문맥 교환)를 같이 찍어서, 처리량 숫자가 흔들려도 원인을 볼 수 있게 했다.

## 3. 진짜 문제

같은 반복 측정에서 혼합 부하가 이상했다.

| 혼합 부하 (읽기 90% / 단건 INSERT 10%), shared_mutex | 처리량 | 잠든 횟수 / 1,000 작업 |
|---|---:|---:|
| 1스레드 | 888k | 0 |
| 2스레드 | 473k | 86 |

**스레드를 늘렸더니 절반으로 느려졌다.** 2스레드에서 작업 1,000개당 86번, 즉 열두 번에 한 번꼴로 스레드가 락을 기다리다 잠든다.

## 4. 원인

수정 전 `Table::insert`는 이렇게 생겼다.

```
unique_lock(mu_)            ← 여기서부터 읽는 쪽은 전부 대기
  id 부여
  프레임 인코딩               (메모리 할당)
  pwrite                     (시스템 콜, µs 단위)
  fileSize_·maxId_·index_ 갱신 (공개)
unlock
```

읽기 하나는 1 µs 안팎인데, 쓰기 하나가 락을 쥐는 시간은 인코딩과 `pwrite`를 합쳐 그보다 길다. 그동안 들어온 읽기는 잠든다. 2스레드면 쓰기 10%마다 다른 스레드가 거의 매번 걸린다.

그런데 이 락은 **`pwrite`를 덮을 필요가 없다.** 이 저장소는 append-only이고, 읽는 쪽은 공개된 `fileSize_` 너머를 읽지 않는다(architecture §12). 쓰는 중인 바이트는 아직 `fileSize_` 너머에 있으니 읽는 쪽은 어차피 못 본다. 락이 정말 지켜야 하는 건 **공개하는 순간**(`fileSize_`·`index_` 갱신)뿐이다.

## 5. 해결안 비교

| 안 | 내용 | 판단 |
|---|---|---|
| **A. 락 분리** | 쓰는 쪽끼리는 새 `writeMu_`로 줄 선다. 인코딩·`pwrite`는 그것만 쥐고 한다. `mu_`는 공개 순간에만 독점으로 잡는다 | **채택.** 원인을 직접 없앤다 |
| B. 쓰기 우선 rwlock | glibc rwlock의 우선순위 속성만 바꾼다 | 읽는 쪽이 `pwrite`를 기다리는 구조는 그대로. 누가 기다리는지만 바뀐다 |
| C. `std::mutex`로 되돌림 | 읽기도 독점 락 | 혼합 부하는 조금 낫지만 읽기 전용에서 약 1.8배 손해 (2절) |
| D. 락 없는 읽기 (RCU) | 인덱스를 노드 복사 방식으로 바꿔 읽는 쪽이 락을 안 잡게 함 | 효과는 가장 크지만 B+ 트리를 다시 짜야 한다. 과제 범위에 비해 과함 |

## 6. 바꾼 것

```
lock_guard(writeMu_)        ← 쓰는 쪽끼리만 줄 섬. 읽는 쪽은 이 락을 모름
  id 부여, 인코딩, pwrite    (실패 시 ftruncate도 여기서)
  unique_lock(mu_)          ← 읽는 쪽이 기다리는 건 이 구간뿐
    fileSize_·maxId_·rowCount_·index_ 갱신
  unlock
unlock
```

- 코드: `src/storage/table.cpp` `Table::insert`, `src/storage/table.h`(멤버 `writeMu_`와 락 규칙 주석)
- 규칙: 공개 상태(`fileSize_`·`maxId_`·`rowCount_`·`index_`·쓰기 불가 플래그)를 바꾸는 건 **두 락을 모두 쥔 쓰는 쪽뿐**이다.
- 회귀 테스트: `tests/storage_test.cpp` `ReadersDoNotWaitForWriterIo`. 쓰는 쪽을 `pwrite` 안에서 멈춰 놓고, 그동안 `findById`·`rowCount`·스캔이 2초 안에 끝나는지 본다. 수정 전 코드에서 돌리면 실패한다(확인함).

## 7. 전후 수치

측정: `minidb_bench_lock`, HTTP를 빼고 `Table` API를 여러 스레드에서 직접 호출. 10만 행에서 시작, 구간당 1초, **5회 반복의 중앙값**(괄호는 최소~최대). "잠듦"은 작업 1,000개당 자발적 문맥 교환 수. 환경은 Docker(Ubuntu 24.04, glibc 2.39), vCPU 2개, 데이터는 ext4 볼륨.

### 7.1 실제 설정 (shared_mutex)

| 작업 | 스레드 | 수정 전 | 수정 후 | 변화 | 잠듦 (전 → 후) |
|---|---:|---:|---:|---:|---:|
| 혼합 90/10 | 1 | 888k (831~1,053) | 776k (567~1,146) | 노이즈 범위 | 0 → 0 |
| 혼합 90/10 | **2** | **473k** (360~544) | **770k** (600~915) | **+63%** | **86 → 20** |
| 혼합 90/10 | 4 | 476k (435~535) | 1,044k (601~1,223) | +119% | 100 → 21 |
| 읽기 전용 | 2 | 1,392k (1,191~1,567) | 1,454k (1,314~1,774) | 노이즈 범위 | 0 → 0 |
| 단건 INSERT | 2 | 601k (502~666) | 530k (528~586) | 노이즈 범위 | 48 → 61 |
| 100행 배치 | 2 | 24k (23~32) | 28k (23~31) | 노이즈 범위 | 498 → 633 |

- 혼합 2스레드는 전후 범위가 겹치지 않는다(최대 544k < 최소 600k). 개선이 노이즈가 아니다.
- 4스레드는 vCPU 2개를 나눠 쓰는 것이라 병렬성이 아니라 "기다리는 스레드가 많을 때"를 본 것이다. 참고용.
- 1스레드는 경합이 없어 락 구조와 무관하다. 차이는 측정 노이즈(±25%)다.

### 7.2 비교용 (읽기도 독점 락)

| 작업 | 스레드 | 수정 전 | 수정 후 |
|---|---:|---:|---:|
| 혼합 90/10 | 2 | 606k (555~966) | 795k (607~1,145) |
| 읽기 전용 | 2 | 769k (580~1,270) | 1,285k (868~1,378) |

독점 락 빌드도 좋아진다. 쓰는 쪽이 락을 짧게 쥐니 읽기끼리 부딪쳐도 덜 기다린다.

## 8. 안전한 이유

- **읽는 쪽이 반쯤 쓴 프레임을 못 본다.** 읽는 쪽은 오프셋을 `fileSize_`와 `index_`에서만 얻고, 둘은 `pwrite`가 끝난 뒤 `mu_` 독점 구간에서만 바뀐다(공개 순서, architecture §12).
- **쓰는 쪽끼리 겹치지 않는다.** 둘 다 `writeMu_`를 잡아야 하므로 같은 오프셋에 쓰지 않는다.
- **쓰는 쪽이 `mu_` 없이 `fileSize_`·`maxId_`를 읽어도 데이터 레이스가 아니다.** 그 값을 바꾸는 쪽은 `writeMu_`를 쥔 쓰는 쪽뿐인데, 지금 그 락은 자기가 쥐고 있다. 동시에 일어나는 건 읽기와 읽기뿐이다.
- **실패 시 자르기**(`ftruncate`)도 공개된 `fileSize_` 뒤만 건드리므로 `mu_` 밖에서 해도 된다. 쓰기 불가 플래그를 세울 때만 `mu_`를 잡는다.
- 검증: TSan 프리셋 전체 테스트 통과, 회귀 테스트가 수정 전 코드에서 실패하고 수정 후 통과.

## 9. 바뀌지 않은 것과 남은 한계

- **쓰기만 하는 부하는 그대로다.** 파일 하나에 덧붙이는 쓰기는 어차피 한 줄로 서야 한다. 이걸 줄이는 방법은 여러 요청을 프레임 하나로 묶는 group commit이다(`refactoring.md`).
- **혼합 부하 2스레드가 1스레드보다 빨라지지는 않는다**(776k → 770k). 이제 락 때문이 아니라, 읽기 하나의 대부분이 `pread` 시스템 콜이고 vCPU가 2개뿐이라서다 [추정]. 코어가 더 많은 환경에서 다시 재야 확인된다.
- 수정 전 shared가 혼합 부하에서 독점 락보다도 느렸던 이유(잠든 횟수는 비슷한데 더 느림)는 확인하지 못했다. glibc rwlock의 대기 경로가 더 무거울 것으로 본다 [추정]. 수정 후에는 잠드는 일 자체가 줄어 이 차이가 의미를 잃었다.

## 10. 재현 방법

```
docker compose run --rm dev
cmake --preset release && cmake --build --preset release
./build/release/minidb_bench_lock --dir /data/lb --threads 1,2 --ms 1000
./build/release/minidb_bench_lock_exclusive --dir /data/lb --threads 1,2 --ms 1000
```

출력 열: `변형,작업,스레드,ops/s,행/s,작업 1,000개당 잠든 횟수`. 수정 전 수치는 `src/storage/table.*`만 부모 커밋 것으로 되돌려 같은 명령으로 얻는다(잠든 횟수 열은 이 커밋에서 벤치에 추가했다). 흔들림이 크니 최소 3회 반복해 중앙값과 범위를 본다.
