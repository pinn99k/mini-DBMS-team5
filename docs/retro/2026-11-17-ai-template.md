미니 DBMS(2026-11-15 설계 ~ 11-17 락 분리)에 `ai-collab-rules` v0.2를 적용하면서 생긴 문제를 정리한다. mini-react(v0.1)에 이은 두 번째 적용이다. 기능 구현 과정의 회고는 `2026-11-16-mvp.md`에 있고, 여기서는 템플릿 자체만 다룬다.

## 1. 한 줄 요약

mini-react 때와 같은 패턴이 반복됐다. **AI와 도구가 실행하는 장치는 돌았고, 사람이 실행하거나 설치해야 하는 장치는 돌지 않았다.** 그리고 v0.2의 핵심 변경인 질문 지도가 첫날 꺼져서(#9), 이번 프로젝트로는 v0.2의 가설("질문 지도로 explain-back 대기가 줄어든다")을 검증하지 못했다.

## 2. 적용 조건

mini-react와 달랐던 점이 결과 해석에 영향을 준다.

| 항목 | mini-react (v0.1) | 미니 DBMS (v0.2) |
|---|---|---|
| 설계 | AI가 설계 후 질문 | Cowork에서 사람이 큰 설계를 먼저 끝냄(#0) |
| 구현 속도 | 12분에 약 1,150줄, 사람이 따라가지 못해 중단 | 하루에 P1~P3 전부, 커밋 하나 +5,423줄 |
| 규칙 위치 | 전역 설치 | 저장소 안 사본 `ai-collab-rules/`, CLAUDE.md에서 3개만 `@` 불러옴 |
| 질문 지도 | 없음 (v0.1) | 템플릿에 있었으나 쓰지 않음 (#9) |

## 3. 문제

### 3.1 핵심 장치가 첫날 꺼졌다

- **현상**: `docs/question-maps/` 폴더가 없다. `ai-collab-design-briefing.md`는 CLAUDE.md에서 불러오지 않았고, CLAUDE.md에 "#9로 대체"라고 적혀 있다.
- **원인**: 템플릿은 "명세 → 질문 → 결정" 순서로 처음부터 설계한다고 가정한다. 이번에는 Cowork에서 큰 설계가 끝난 상태로 들어왔다. 템플릿에 "설계를 받아서 시작하는" 모드가 없어서, 두 작업 방식이 충돌했고(MVP 회고 3.2) 질문 지도를 끄는 쪽으로 정리됐다.
- **결과**: 실험의 처치 변수가 빠졌다. 이번 데이터는 v0.2의 검증이 아니라 **v0.1 실패 방식의 재확인**이다. 템플릿의 다른 부분(MODE, `docs/adr/`, `docs/design-memos/`)도 쓰지 않고 `decisions.md` 로그로 바꿨다.

### 3.2 커밋 훅이 설치되지 않았고, 아무도 몰랐다

- **현상**: `.git/hooks/pre-commit`, `.git/ai-alarms.log`, `.git/ai-estimate`가 모두 없다.
- **원인**: 훅 설치는 템플릿 README 4절 5단계의 수동 작업이다. 빠져도 알려 주는 장치가 없다. 조용한 실패다.
- **결과**:
  - 커밋 본문의 "예상 대비"는 훅이 대조하지 않은 자기 신고다. 규칙의 형식만 남고 기능은 없었다.
  - `Lexer::next` CC 39는 MVP 커밋에서 생겼지만, 커밋 경보가 아니라 다음 날 phase-audit에서 잡혔다.

### 3.3 커밋 단위가 규칙과 맞지 않았다

- **현상**: MVP는 커밋 하나에 77파일, +5,423줄이다. CLAUDE.md는 "마일스톤 하나 이하/커밋"이고 마일스톤은 M1~M15다. 처음 두 커밋에는 5줄 요약 본문도 없다(5줄 형식은 세 번째 커밋부터).
- **원인** [추정]: 하루 만에 P1~P3를 끝까지 구현했고, "다음 Phase는 사람 확인 후"라는 게이트를 실제로 걸지 않았다. 근거는 Phase 경계에 커밋이 없다는 점이다.
- **결과**: 훅이 설치돼 있었어도 경보가 커밋 하나에 몰렸을 것이다. 커밋 단위 경보와 변경 요약은 커밋이 작다는 전제 위에서만 의미가 있다.

### 3.4 explain-back: 대기 19건, 완료 0건

- **현상**: mini-react는 11건 대기·0건 완료였다. 이번에는 MVP 직후 17건, 락 분리(#19) 뒤 19건이 됐고 완료는 0건이다.
- MVP 회고 7-4에 "AI가 쓴 핵심 로직은 기능 완성 직후 바로 이해 검사를 한다"고 적었다. 다음 날 대기는 2건 늘고 닫힌 건 없다.
- **원인**: 교훈이 문서에만 있고 실행 계기(trigger)가 없다. v0.2는 일부러 강제를 넣지 않았다. 이유는 "질문 지도와 강제를 함께 넣으면 어느 쪽 효과인지 알 수 없다"였다. 그런데 질문 지도가 꺼지면서 강제를 뺀 이유도 함께 사라졌다.
- **의미**: 이번에는 사람이 큰 설계를 직접 걸었는데도 대기가 쌓였다. 대기 항목은 대부분 AI가 정한 세부(알려주기 7건, 구현 후 6건, 락 분리 2건)와 위임 4건이다. 사람이 걷지 않은 부분만 대기로 남는다는 뜻이다.

### 3.5 문서가 늘었다

- **현상**: v0.2 목표는 "사람이 작업 중에 읽는 문서는 질문 지도 1장"이었다. 실제로는 `docs/` 아래 문서가 14종 이상, 약 2,000줄이다(소스 3,322줄).
- "같은 커밋에서 갱신" 의무가 세 곳으로 늘었다: `architecture.md` ↔ 코드, `decisions-summary.md`(#17), `guide.md`.
- **역설**: MVP 회고 3.1의 교훈은 "원본은 하나, 나머지는 뷰"였다. 그 뒤에 사본 문서(#17)를 더했다. 뷰를 자동으로 만들 수단이 없어서 사본을 손으로 동기화하게 됐다.
- **원인**: 독자가 세 종류(AI 구현자, 팀원, 배우는 사람)인데 템플릿의 문서 체계는 AI·작업자용 하나뿐이다. 독자가 나타날 때마다 문서를 하나씩 더했다.

### 3.6 한쪽 문 경계를 AI가 스스로 판정했다 [추정]

- **현상**: CLAUDE.md의 "Stop and ask" 목록에 write ordering, error→status mapping이 있다. 그런데 다음 결정의 "정한 사람"은 AI다.
  - #6 `pwrite(off = fileSize)` 고정, `O_APPEND` 금지 (쓰기 순서와 실패 시 동작)
  - #10 중 CLI 종료 코드 0/1/2 (에러 → 상태)
  - #12 503 전달 방식, 거절 레인 (에러 → 응답)
- **판단**: 기준선 `[고정]` 규칙의 구현 세부로 볼 수도 있다. 위반인지 회색지대인지 판정하는 주체가 AI라서 이 기록만으로는 가를 수 없다.
- **모름**: one-way-door 스킬이 실제로 호출됐는지는 이 저장소에 기록이 없다. 확인하려면 해당 세션 기록을 검색해야 한다.
- **구조적 문제**: 한쪽 문 목록이 있어도, 어떤 결정이 그 목록에 해당하는지 분류하는 일은 AI가 한다. 분류가 틀려도 드러날 경로가 사후 검토뿐이다.

## 4. 잘 된 것

- **phase-audit이 돌았다.** mini-react의 weekly-audit은 0회였고, 이번에는 2회다. 침식도는 0.56 → 0.38로 내려갔다. 주기를 "주 1회"에서 "단계 끝"으로 바꾼 v0.2 변경이 효과가 있었다 [추정: 단계가 끝나는 시점이 명확해서 실행 계기가 생겼다].
- **도구가 실제 버그를 찾았다.** phase-audit이 `Table::recover`와 `dumpTable`의 CC 19를 짚었고, 들여다보니 같은 판정 규칙을 따로 구현해 이미 어긋나 있었다(dump가 시작 거부될 파일을 ok로 봄). 지표를 경보로만 쓰고 사람이 보게 하는 설계가 의도대로 작동했다.
- **사람의 기술 결정 두 건은 질이 좋았다.**
  - #18 공용 스캐너: phase-audit 결과를 보고 결정
  - #19 락 분리: 벤치에서 문맥 교환(작업 1,000개당 86회)을 잰 뒤 결정. 혼합 부하 473k → 770k ops/s
- **결정 추적성**: 정한 사람(사람·위임·AI)과 이유가 #0~#19로 남아 "왜"를 따라갈 수 있다. 덧붙이기 전용 로그 형식은 그대로 유지할 만하다.

## 5. 메커니즘: 템플릿의 두 가정

템플릿은 두 가지를 가정한다. 이번 결과는 둘 다 깨졌다.

### 5.1 가정 1: 사람은 구현 전에 결정한다

구현 전에 사람에게 넘긴 기술 결정(D1~D4)은 4건 모두 "추천대로", 즉 위임이었다. 반면 사람이 직접 고른 기술 결정(#18, #19)은 둘 다 **결과물과 수치가 생긴 뒤**였다. 나머지 사람 결정(#1, #8, #9, #17)은 환경·문서·작업 방식이다.

행동경제학으로 보면, 사람은 추상적인 선택지보다 구체적인 증거 앞에서 결정을 잘 내린다. 명세만 보고 "frame_len 범위 검사를 할까"를 고르는 것과, 벤치 결과에 "2스레드가 1스레드보다 느리다"가 찍힌 뒤 락 구조를 고르는 것은 다른 과제다. 앞쪽은 상상할 재료가 없어서 추천을 받게 되고, 뒤쪽은 관찰한 문제가 있어서 판단이 선다.

### 5.2 가정 2: 사람의 행동은 끌어오기(pull)로 충분하다

AI의 기본 동작은 코드를 밀어내는 것(push)이다. 사람의 이해 확인과 훅 설치는 사람이 스스로 해야 하는 선택 사항(opt-in)이다. 기본값이 생성 쪽에 걸려 있으니 대기는 쌓이기만 한다.

행동을 미리 묶어 두는 장치(commitment device) 없이 의지에만 기대는 결심과 같은 구조다. "직후에 검사한다"는 교훈을 문서에 적어도, 그 문서를 열게 만드는 계기가 없으면 실행되지 않는다. 반대로 phase-audit이 돈 이유는 "단계가 끝났다"는 명확한 계기가 있었기 때문이다 [추정].

## 7. 열린 질문

**#18·#19가 잘 된 이유는 "측정 뒤에 결정해서"인가, "MVP를 다 만든 뒤라 시스템 전체를 알고 있어서"인가.**

두 설명은 v0.3 후보 A의 설계를 다르게 만든다. 앞쪽이 맞으면 결정 시점마다 측정을 붙이면 된다. 뒤쪽이 맞으면 작은 단위로 먼저 만들어 보고(스파이크) 결정하는 흐름이 필요하다. 다음 프로젝트에서 MVP 전에 측정 근거를 붙인 결정을 하나 만들어 보면 둘을 가를 수 있다.
