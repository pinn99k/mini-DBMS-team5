## 1. 한 줄 요약

기능은 하루 만에 다 됐다. 시간을 가장 많이 쓴 곳은 코드가 아니라 **환경(WSL2·Docker·TSan)과 라이브러리의 실제 동작(httplib)**이었다. 가장 큰 남은 리스크는 **내가 직접 쓰지 않은 코드에 대한 이해**다. explain-log 대기가 17건이다.

## 2. 환경

### 2.1 빌드 환경이 없었다
- **문제**: Windows 호스트에 cmake·g++가 없고, WSL에는 Docker Desktop용 배포판만 있었다.
- **해결**: Docker 개발 컨테이너(Ubuntu 24.04)로 통일했다(#1).
- **교훈**: 팀 프로젝트의 첫 작업은 "모두 같은 명령으로 빌드되는가"를 확인하는 것이다.

### 2.2 TSan이 10번 중 9번 시작하자마자 죽었다
- **문제**: `FATAL: ThreadSanitizer: unexpected memory mapping`.
- **원인**: WSL2 커널 6.6의 `vm.mmap_rnd_bits=32`. 주소 무작위화(ASLR) 범위가 TSan이 가정하는 메모리 배치보다 넓다.
- **해결**: `setarch $(uname -m) -R`로 ASLR을 끄고 실행하니 10/10 통과했다. 이를 위해 compose에 `seccomp:unconfined`를 넣었고, tsan 프리셋이 ctest에 래퍼를 자동으로 건다(#7).
- **교훈**: 1번 성공했다고 됐다고 보면 안 된다. 실패 확률이 있는 문제는 반복 실행으로 판정한다(그냥 실행 1/10, 래퍼 10/10).

### 2.3 소스 폴더에서 벤치를 돌리면 엉뚱한 것을 잰다
- **문제**: 컨테이너의 `/work`는 Windows D: 드라이브를 연결한 9p 파일시스템이다. 느리고 fsync 동작도 다르다.
- **해결**: 빌드 산출물과 테이블 데이터를 Docker named volume(ext4)에 둔다. 덤으로 볼트에 대용량 파일이 쌓이지 않는다.

### 2.4 줄바꿈(CRLF)
- **문제**: 호스트 git이 `autocrlf=true`라서, 체크아웃하면 CRLF가 된다. 컨테이너의 셸 스크립트가 깨질 위험이 있었다.
- **해결**: `.gitattributes`에 `* text=auto eol=lf`.

## 3. 설계와 문서

### 3.1 같은 규칙이 세 문서에 있었다
- **문제**: 프레임 포맷과 손상 규칙이 지시서(brief), decisions.md, architecture.md에 중복돼 있었다. 결정 하나(D4)를 반영하는 데 세 파일을 고쳤다.
- **해결**: 설계는 `architecture.md` 하나로 합치고, 결정은 덧붙이기 전용 로그(`decisions.md`)로 분리했다. Phase별 지시서는 `archive/`로 보관했다(#8).
- **교훈**: 문서도 DB와 같다. 원본은 하나이고, 나머지는 원본을 가리키는 뷰여야 한다.
- **실수**: 보관하기로 한 지시서에 개정 메모를 넣었다가 되돌렸다. 문서의 역할을 정하기 전에 고쳤기 때문이다.

### 3.2 작업 방식 두 가지가 충돌했다
- **문제**: 지시서는 "AI가 설계하고 사람이 승인"인데, ai-collab 규칙은 "질문 지도를 내고 사람이 하나씩 결정"이었다.
- **해결**: 큰 설계는 Cowork에서 이미 끝났으므로, 세부 설계와 로직은 AI가 정하고 사람은 한쪽 문 결정만 하기로 했다(#9).

### 3.3 설계 검토에서 찾은 구멍 4개
구현 전에 브리프를 읽다가 찾았고, 모두 추천안으로 정했다(위임).

| # | 구멍 | 해결 |
|---|---|---|
| #2 | 중간 프레임의 `frame_len`이 깨지면 정상 프레임까지 꼬리 손상으로 잘림 | 길이 범위 밖이면 시작 거부 + 잘라낼 바이트는 `.torn`으로 보관 |
| #3 | 결과를 받는 쪽이 "그만"을 알릴 방법이 없음 | `RowSink::row()`가 bool을 반환 |
| #4 | 쓰기 실패 후 되돌리기(`ftruncate`)까지 실패하면 어떻게 할지 없음 | 그 테이블을 쓰기 불가로 표시 |
| #5 | 생성 중 끊긴 8B 미만 파일이 시작 거부됨 | 헤더를 다시 씀 |

### 3.4 architecture.md가 읽기 어려웠다
- **문제**: 구현자(와 AI)용 참조 문서라 용어 설명이 없고 `[고정]`·`#N` 같은 참조 표시가 많았다.
- **해결**: 배우는 사람용 `docs/guide.md`를 따로 만들었다. 읽는 순서는 guide → bench → architecture.
- **교훈**: 문서마다 독자를 먼저 정해야 한다. 설계 문서와 학습 문서는 다른 문서다.

## 4. 구현과 테스트

### 4.1 첫 빌드
전 모듈을 한 번에 쓰고 첫 빌드에서 실패한 것은 링크 오류 하나였다. `concurrency_test`가 `ThreadPool`을 쓰는데 server 라이브러리를 링크하지 않았다. 첫 테스트 실행에서는 9개 중 8개가 통과했다(실패 1개는 5.1).

### 4.2 CMake 환경 변수가 쪼개졌다
- **문제**: 셸 테스트에 TSan 래퍼(`setarch;x86_64;-R`)를 환경 변수로 넘기려 했다. 그런데 CMake의 `ENVIRONMENT` 속성은 세미콜론을 리스트 구분자로 본다.
- **해결**: `string(REPLACE ";" " " ...)`로 공백 구분 문자열로 바꿔 넘긴다.

### 4.3 debug 테스트가 153초 걸렸다
- **원인 1**: `-O0` + ASan. ASan 권장인 `-O1`로 바꾸니 87초.
- **원인 2**: 테스트 자체는 19초인데, 100만 건 테스트 뒤 종료 시점의 LeakSanitizer 검사가 60초를 썼다.
- **해결**: 100만 건 테스트는 debug에서만 건너뛰고 tsan·release에서 돌린다(#15). debug 전체가 4.4초가 됐다.
- **교훈**: "테스트가 느리다"에서 멈추지 말고 시간을 나눠 잰다. 범인이 테스트 코드가 아니라 종료 시점의 도구였다.

### 4.4 내 실수
- 렉서 테스트에서 토큰 개수를 잘못 셌다. 첫 빌드 전에 발견해 고쳤다.
- README의 `printf` 예시가 Python 문자열 처리 중 실제 줄바꿈으로 깨졌다. 다시 읽다가 발견해 고쳤다.
- 교훈: 생성한 문서·테스트도 한 번은 결과를 직접 보고 확인한다.

### 4.5 수동 테스트에서 발견한 한계: 꼬리 손상 뒤 id 재사용
- **현상**: 마지막 프레임(id 4)을 잘라낸 뒤 INSERT하니 새 행이 다시 id 4를 받았다.
- **원인**: 다음 id = "파일에 남은 최대 id + 1"(기준선 `[고정]` 규칙). 정전으로 마지막 묶음이 사라지면 그 번호가 다시 나간다.
- **판단**: 과제 범위에서는 의도된 동작이다. 개선은 다음 id를 따로 영속화하는 것(`refactoring.md`).
- **교훈**: 자동 테스트는 "설계대로 동작하는가"를 보고, 수동 테스트는 "설계가 맞는가"를 보게 된다.

### 4.6 수동 테스트 출력이 헷갈렸다
- `grep`은 stdout만 거르고 에러(stderr)는 그대로 화면에 나와 줄이 섞였다.
- 서버를 `&`로 띄우니 로그와 프롬프트가 겹쳤다.
- 버그는 아니었지만, 안내할 때 "어떤 출력이 정상인지"를 먼저 알려 줬어야 했다.

## 5. 서버와 성능

### 5.1 동시 클라이언트 테스트 실패: 연결 하나가 워커 하나를 붙잡는다
- **문제**: 클라이언트 8개 · 워커 4개 테스트에서 요청 4개가 실패했다.
- **원인**: cpp-httplib는 연결 단위로 워커를 배정하고, keep-alive 연결이 끝날 때까지 같은 워커가 그 연결을 맡는다. 뒤쪽 4개 클라이언트는 큐에서 기다리다 클라이언트 읽기 타임아웃(5초)에 걸렸다.
- **해결**: 테스트는 클라이언트 타임아웃을 늘려 통과시켰다. 구조적 한계는 architecture §19에 남기고, 이벤트 루프 방식을 refactoring.md 후보로 올렸다.
- **교훈**: 스레드 풀의 "워커 수"가 동시 요청 수인지 동시 연결 수인지는 라이브러리가 정한다. 직접 확인해야 안다.

### 5.2 요청마다 40 ms 지연
- **문제**: 요청 640개에 14초.
- **원인**: 응답을 헤더와 본문 두 번에 나눠 쓴다. Nagle 알고리즘(작은 패킷을 모으려고 기다림)과 상대의 지연 ACK가 서로를 기다렸다.
- **해결**: 서버에서 `TCP_NODELAY`를 켜니 7초, 테스트 클라이언트까지 켜니 0.22초(#14).
- **교훈**: 응답 하나에 정확히 수십 ms씩 걸리면 먼저 Nagle을 의심한다.

### 5.3 httplib로는 503을 보낼 수 없었다
- **문제**: apt 판 0.14.3의 `TaskQueue::enqueue`는 void라 거절 신호가 없다.
- **해결**: 큐가 가득 차면 연결을 전용 스레드(거절 레인)로 넘기고, 그 스레드에서 pre-routing 핸들러가 즉시 503을 보낸다(#12).
- **교훈**: 요구사항("가득 차면 503")이 라이브러리의 확장 지점과 맞는지 헤더를 직접 읽고 확인한다. 추정으로 설계하면 구현 단계에서 막힌다.

### 5.4 httplib는 컴파일된 판이었다
- **문제**: apt 패키지가 헤더 전용이 아니라 `.so`였다. 빌드할 때 쓴 define(OpenSSL 등)이 다르면 클래스 레이아웃이 어긋난다(ODR 위반).
- **해결**: pkg-config로 연결해 같은 define을 받는다(#11).

### 5.5 shared_mutex가 이기지 못했다
- **결과**: 읽기 전용 부하에서도 "읽기도 독점 락"과 비슷하거나 더 빨랐다. 혼합 부하에서는 shared가 절반으로 떨어졌다.
- **해석**: 읽는 쪽이 락을 잡는 시간이 트리 조회 수십 ns뿐이라 경합이 거의 없다. 혼합 부하에서 떨어진 원인은 [추정]이다.
- **한계**: 컨테이너 vCPU가 2개다. 결론이 아니라 관찰이다.

## 6. 협업 방식

- **잘 된 것**: 큰 설계(사람) → 세부와 구현(AI) → 수동 테스트(사람)로 나누니 하루 만에 끝까지 갔다. 문제마다 결정 번호가 남아 "왜"를 추적할 수 있다.
- **안 된 것**: 코드 전부를 AI가 썼고, 사람은 아직 핵심 로직을 직접 설명해 보지 않았다. 과제 평가 기준("핵심 로직을 설명할 수 있어야 한다")에 비추면 지금이 가장 큰 리스크다.
- **CI는 넣지 않기로 했다**: 미니 프로젝트라 로컬 컨테이너 테스트로 충분하다고 판단했다. 중요한 프로젝트에서 도입한다.
- **팀원과 환경 공유**: 레포가 개인 private이라, Dockerfile·compose·.gitattributes 원문을 담은 프롬프트로 공유하기로 했다.

## 7. 다음에 다르게 할 것

1. **문서의 독자를 먼저 정한다.** 참조용(architecture)과 학습용(guide)을 처음부터 나눈다.
2. **라이브러리 확장 지점은 설계 단계에서 헤더로 확인한다.** 503 문제를 구현 전에 알 수 있었다.
3. **확률적 실패는 반복 실행으로 판정한다.** TSan과 동시성 테스트 모두 해당한다.
4. **AI가 쓴 핵심 로직은 기능이 완성된 직후 바로 이해 검사를 한다.** 대기가 쌓이면 발표 직전에 몰린다.
