## 1. 환경

## 2. 인덱스 조회 vs 전체 스캔 (Phase 2)

스키마 `name VARCHAR(32), age INT`. 데이터는 엔진 API로 1000행 배치를 넣어 만들었다. 조회는 Executor 경로(바인딩 + 계획 + 실행 + sink)로 쟀다.
- id 조회: 고정 시드 무작위 id 1000개, 워밍업 100회.
- 스캔: `WHERE name = '<가운데 값>'`, 5회 반복의 중앙값.

| 행 수 | 삽입 (s) | 파일 (MB) | 열기 + 인덱스 재구성 (ms) | id 조회 중앙값 (µs) | p99 (µs) | 전체 스캔 중앙값 (ms) | 배율 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 10,000 | 0.02 | 0.29 | 2.0 | 1.3 | 1.6 | 0.61 | 464× |
| 100,000 | 0.07 | 3.04 | 11.8 | 1.7 | 4.9 | 4.13 | 2,491× |
| 1,000,000 | 1.26 | 31.38 | 135.5 | 1.9 | 6.9 | 45.53 | 24,361× |

- **조회는 거의 일정하고 스캔은 선형이다.** 행이 100배가 되는 동안 id 조회는 1.3 → 1.9 µs(트리 높이 2 → 3), 스캔은 0.61 → 45.5 ms로 늘었다.
- id 조회 1.9 µs의 대부분은 트리 탐색이 아니라 `pread` 두 번(길이 4 B + payload)이다. 노드 용량이 128이라 100만 건에서도 높이가 3이다.
- 재시작 비용: 100만 건(31 MB)의 복구 스캔 + CRC 검사 + 레코드 디코드 + 벌크 로드가 136 ms다. 벌크 로딩은 리프를 꽉 채우므로, 순차 삽입(반반 분할, 리프 충전율 약 50%)으로 만든 트리보다 작다.

## 3. SQL 경로: INSERT 100만 문장

`.sql` 파일(41.8 MB)에 한 줄짜리 INSERT 100만 개를 넣고 `minidb run`으로 실행했다. 문장마다 프레임 1개, 쓰기 1번이다.

| 항목 | 값 |
|---|---|
| 걸린 시간 | 2.14 s (약 47만 문장/s) |
| 최대 RSS | 118 MB |
| 결과 파일 | 44.9 MB (프레임 1M개. 배치로 만든 2장의 31.4 MB보다 프레임 오버헤드 12 B × 1M만큼 큼) |

RSS의 대부분은 `.sql` 파일 전체를 문자열로 읽은 것(42 MB)과, 순차 삽입으로 50%만 찬 인덱스다. Parser는 문장 단위로 당겨 오므로 토큰 배열은 만들지 않는다.

## 4. 스트리밍 메모리 (Phase 3)

서버에 `SELECT * FROM t`(100만 행)를 보내고, 요청 전후 서버 프로세스의 최대 RSS(`VmHWM`)를 비교했다.

| 항목 | 값 |
|---|---|
| 응답 | 1,000,002줄 (columns 1 + 행 1M + 마지막 `{"ok":true,"rowCount":1000000}`), 25.7 MB |
| 걸린 시간 | 0.18 s |
| 서버 VmHWM | 요청 전 24,320 kB → 요청 후 24,448 kB (+128 kB) |

25.7 MB를 보내는 동안 서버 메모리는 128 kB만 늘었다. 결과를 모으지 않고 프레임 버퍼(64 KiB)와 NDJSON 버퍼(16 KiB)만 쓰기 때문이다. 요청 전 24 MB에는 100만 건 인덱스(벌크 로드)가 포함된다.

## 5. 락 방식·배치 처리량 (Phase 3)

HTTP를 빼고 `Table` API를 여러 스레드에서 직접 불렀다(테이블 10만 행에서 시작, 구간당 1.5초). `exclusive`는 같은 코드를 읽기도 `unique_lock`으로 빌드한 것이다.

ops/s (배치는 배치 수/s, 괄호는 행/s):

| 작업 | 스레드 | shared_mutex | 읽기도 unique_lock |
|---|---:|---:|---:|
| 읽기 전용 (findById) | 1 | 1,282,168 | 1,377,946 |
| | 2 | 1,734,586 | 1,891,516 |
| | 8 | 1,514,402 | 1,849,897 |
| 읽기 90% / 단건 INSERT 10% | 1 | 994,586 | 1,172,547 |
| | 2 | 492,708 | 1,114,219 |
| | 8 | 608,244 | 1,260,374 |
| 단건 INSERT | 1 | 1,254,890 | 1,315,464 |
| | 2 | 743,383 | 867,497 |
| 100행 배치 INSERT | 1 | 20,850 (2.09M 행) | 16,414 (1.64M 행) |
| | 2 | 17,636 (1.76M 행) | 26,192 (2.62M 행) |

관찰:
- **shared_mutex가 이기지 못한다.** 읽는 쪽이 락을 잡는 구간이 트리 조회(수십 ns)뿐이고, 파일 읽기(`pread`, ~1 µs)는 락을 놓은 뒤에 하기 때문이다(architecture §12). 경합할 임계 구역이 거의 없으면 읽기 락을 공유해도 얻을 게 없다. 오히려 `pthread_rwlock`의 비용이 더 크다.
- 혼합 부하에서 shared가 2스레드부터 절반으로 떨어진다. [추정] glibc rwlock의 writer 대기와 reader 재진입이 vCPU 2개에서 서로를 밀어낸다. 확인하려면 `perf`로 futex 대기 시간을 봐야 한다.
- **배치가 행 처리량을 높인다.** 단건 INSERT는 1.25M 행/s, 100행 배치는 2.09M 행/s다. 배치는 시스템 콜과 락 획득을 100행에 한 번만 한다.
- vCPU가 2개라 스레드 4·8개 구간은 코어를 나눠 쓰는 것일 뿐, 병렬성을 측정한 것이 아니다.

## 6. 해석의 한계

- 페이지 캐시가 데워진 상태다. 차가운 캐시(디스크 읽기)라면 스캔과 조회 모두 느려지고, 차이는 더 벌어진다.
- fsync는 측정에 넣지 않았다. CLI는 끝날 때 한 번, 서버는 1초마다 한 번이다.
- vCPU 2개 환경이다. 락 비교는 코어가 더 많은 환경에서 다시 재야 결론을 낼 수 있다.
- 단일 실행 결과다. 반복 측정과 분산은 아직 없다.
